# OkCode 第十阶段：Skill 系统 Spec

## 背景

OkCode 已经具备工具系统、MCP 接入、提示词管线、上下文管理、长期记忆和统一斜杠命令机制。第九阶段的命令系统已经把“斜杠输入先由本地分流器识别，再决定是否进入 Agent 对话”的边界建立起来，并明确为后续 Skill 系统留下扩展位置。

当前用户在反复使用 OkCode 时，仍然需要手动输入相同或高度相似的提示词，例如提交前检查、代码审查、测试修复、学习笔记整理、特定项目 SOP 等。这些提示词往往包含固定步骤、固定约束、固定工具偏好和少量参数。继续靠临时自然语言输入会造成重复劳动，也会让模型每次重新理解任务边界，增加跑偏概率。

本阶段要把可复用的 AI 操作封装成 Skill。Skill 是一个带元信息的 Markdown 能力定义：启动时只暴露名称和一句说明，真正使用时再按需加载完整 SOP 指令和专属工具，并用工具白名单缩小模型当前可见工具范围，提高模型选对工具的概率。

## 目标

- 建立本地 Skill 定义格式，让单文件 Skill 和目录型 Skill 都能被发现、解析、校验和加载。
- 支持项目目录、用户目录、内置目录三级 Skill 来源，并按项目高于用户高于内置的优先级处理同名覆盖。
- 实现两阶段加载：启动时只注入 Skill 名称和一句说明；激活时再加载完整 SOP 指令、参数替换结果和专属工具。
- 让已激活 Skill 的完整指令稳定出现在后续每轮系统上下文中，多个 Skill 可以同时激活。
- 支持共享当前对话和独立对话两种执行模式，覆盖“结果直接留在主历史”和“隔离跑完后摘要回流”两类工作流。
- 用工具白名单限制 Skill 执行时模型可见工具，同时保证系统级 Skill 加载工具不受白名单影响。
- 提供内置 `/skill` 列表命令，支持查看可加载和已激活 Skill；普通 Skill 通过 LoadSkill 工具激活，不自动占用斜杠命令空间。
- 提供 commit、review、test 三个内置样板 Skill。

## 功能需求

- **F1：Skill 定义格式**  
  单个 Skill 使用 YAML frontmatter 加 Markdown 正文定义。frontmatter 保存元信息，正文保存发给模型的 SOP 指令。正文支持参数占位符，用户通过斜杠命令或加载工具传入参数后，系统在激活时完成替换。参数缺失时必须给出可理解的错误或提示，不能把未替换占位符直接注入模型上下文。

- **F2：frontmatter 元信息**  
  每个 Skill 的 frontmatter 至少表达唯一名字、一句话说明、可见工具白名单、执行模式、独立执行时带入多少历史、可选指定模型六类信息。唯一名字用于覆盖、斜杠命令、加载工具参数和激活状态标识。一句话说明用于启动期注入和帮助展示，不能依赖读取正文才能理解用途。

- **F3：目录型 Skill 包**  
  系统支持目录型 Skill。一个目录可以包含入口 Markdown、专属工具的 schema 和实现脚本，整套作为一个能力包被发现、校验、热更新和加载。目录型 Skill 的入口 Markdown 仍然使用同一套 frontmatter 与正文规则。专属工具只有在对应 Skill 被加载后才进入该 Skill 的可用工具集合，不污染普通对话的默认工具列表。

- **F4：三级来源与覆盖规则**  
  系统从内置目录、用户目录、项目目录三个来源发现 Skill。同名 Skill 按项目目录高于用户目录高于内置目录覆盖。被覆盖的低优先级 Skill 不再出现在启动期 Skill 列表、帮助输出或斜杠命令候选中。不同来源的有效 Skill 必须保持稳定排序，便于帮助、补全和测试断言。

- **F5：单个文件失败隔离**  
  Skill 文件或目录包解析失败时，只跳过该单个 Skill，并把失败原因记录为可诊断信息；其他 Skill 继续可用。解析失败包括 frontmatter 缺失、YAML 语法错误、必填字段缺失、正文为空、目录包入口缺失或目录包内部声明不完整。失败隔离不适用于已成功解析但全局校验失败的情况。

- **F6：启动期全局校验**  
  启动期完成 Skill 元数据发现后，必须校验所有成功解析 Skill 的可见工具白名单。白名单中出现当前系统无法提供的工具名时，启动必须失败并指出 Skill 名称和不存在的工具名，不能等到模型调用时才发现。Skill 加载工具是系统级工具，永远可用，不受任何 Skill 白名单收窄影响。

- **F7：两阶段加载**  
  启动期只把有效 Skill 的名字和一句说明注入模型可见上下文，不注入完整正文、专属工具实现细节或长 SOP。模型需要使用某个 Skill 时，必须通过系统级 LoadSkill 工具按名称加载并激活完整 SOP、参数替换结果和专属工具；用户也可以通过自然语言要求模型使用某个 Skill，由模型调用 LoadSkill 完成激活。LoadSkill 工具不受 Skill 工具白名单约束，加载结果必须可被后续回合复用，避免同一 Skill 在同一对话中反复读取和重复注入。

- **F8：激活指令注入位置**  
  Skill 激活后，完整 SOP 指令必须出现在环境上下文中最显眼的位置，并且每轮 Provider 请求重建时都会保留。多个 Skill 可以同时激活，系统要以可预测顺序呈现每个 Skill 的名称、说明和完整指令，避免不同 Skill 的规则混在一起无法审计。

- **F9：共享执行模式**  
  执行模式为共享当前对话时，Skill 在当前会话历史中运行。用户触发 Skill 后，参数替换后的任务进入主对话，模型输出、工具调用和结果沿用现有普通回合的历史原子提交规则。共享模式适合需要延续当前上下文并把结果长期保留在主历史里的任务。

- **F10：独立执行模式**  
  执行模式为独立对话时，Skill 在隔离的临时对话中运行。系统根据 Skill 元信息选择带入的历史范围，跑完后只把可读摘要、关键结果和必要后续动作回流到主历史。独立对话中的中间消息和工具细节不得无条件污染主历史；如果独立执行失败，主历史只记录失败摘要和可诊断原因。

- **F11：独立模式历史范围**  
  独立执行必须支持“带多少历史进去”的配置。该配置至少能表达不带历史、带最近部分历史、带当前压缩摘要或带安全范围内全部可用历史。实际带入内容必须遵守现有上下文预算、工具消息配对和摘要边界约束，不能为了满足 Skill 配置破坏 Provider 消息合法性。

- **F12：工具白名单收窄**  
  Skill 激活后，该 Skill 的可见工具白名单用于收窄当前模型可见工具。模型在执行该 Skill 时只应看到白名单允许的普通工具、该 Skill 专属工具，以及系统级 Skill 加载工具。多个 Skill 同时激活时，系统必须采用明确且可测试的工具集合合并规则，保证不会意外扩大到全量工具。

- **F13：Skill 列表命令与补全**  
  系统提供内置 `/skill` 命令，用于列出当前已加载并可被 LoadSkill 激活的 Skill 名称、来源优先级和一句话说明；如已有激活 Skill，也显示其激活状态。普通 Skill 不自动注册成各自的斜杠短命令，避免把命令空间和 Skill 空间混在一起。`/skill` 必须出现在帮助和补全候选中，输出内容来自 Skill 注册表元数据。只有 `/skill` 这个命令名需要与内置命令和别名做冲突检查；普通 Skill 名称只需要在 Skill 注册表内部保持唯一，允许与斜杠命令同名。

- **F14：热更新与激活快照**  
  系统支持在运行中刷新 Skill 定义。热更新后，新增、修改、删除、解析失败和覆盖关系变化都能反映到启动期 Skill 列表、`/skill` 输出、补全候选和后续 LoadSkill 结果。已经激活的 Skill 固定使用激活时的快照；即使源文件后来被修改或删除，当前会话也继续使用该快照。只有用户执行 `/clear` 清空对话，或模型/用户显式重新加载同名 Skill 时，才切换到热更新后的最新有效版本；如果重新加载时该 Skill 已不存在或解析失败，必须保留旧快照并提示原因。

- **F15：清空对话联动**  
  用户清空对话时，当前内存消息、累计计数和会话边界按现有规则重置，同时清掉所有已激活 Skill。清空后下一轮系统上下文只保留启动期 Skill 名称和说明，不再携带此前激活的完整 SOP。

- **F16：内置样板 Skill**  
  本阶段内置 commit、review、test 三个样板 Skill。commit 用于提交前整理和提交信息生成，review 用于代码审查，test 用于运行和修复测试。三个样板必须使用与用户自定义 Skill 相同的定义格式、加载路径、白名单校验和 LoadSkill 激活机制，不走单独硬编码分支。

## 非功能需求

- **N1：低启动成本**  
  启动期只读取和注入 Skill 元数据，不读取或注入所有完整 SOP。大量 Skill 存在时，启动上下文增长应主要由“名称 + 一句话说明”决定，而不是由正文长度决定。

- **N2：可诊断性**  
  Skill 解析失败、覆盖关系、白名单缺失工具、Skill 名称冲突、参数缺失、专属工具加载失败和独立执行失败，都必须有面向用户或开发者可定位的信息，至少包含 Skill 名称、来源路径或来源类别、失败原因。

- **N3：历史安全性**  
  共享模式继续遵守现有历史原子提交规则；独立模式不能把未完成工具调用、不完整工具结果、临时推理过程或失败的半成品消息写入主历史。

- **N4：上下文稳定性**  
  激活后的 Skill 指令在每轮系统上下文中的位置和顺序必须稳定，避免因为字典遍历、文件系统顺序或热更新导致不可预测提示词重排。

- **N5：工具安全边界**  
  Skill 工具白名单只影响模型可见工具，不绕过现有权限系统、黑名单、工作区限制、MCP 连接规则或命令执行安全策略。专属工具执行失败必须转为结构化工具结果或可诊断错误，不能让运行时崩溃。

- **N6：Windows 兼容性**  
  Skill 路径发现、目录包加载、脚本执行、热更新和错误展示必须适配 OkCode 的 Windows 运行环境，不假设 Unix 路径分隔符、可执行权限位或 shell 行为。

- **N7：可测试性**  
  Skill 发现、frontmatter 解析、覆盖、失败隔离、白名单启动失败、加载工具不受白名单限制、指令注入、两种执行模式、斜杠命令、补全、热更新、清空联动和内置样板都必须能用自动化测试验证，涉及模型请求的场景使用可控替身。

## 不做的事

- 不做 Skill 市场分发、远程下载、发布、订阅、评分或搜索。
- 不做 Skill 版本管理、版本约束、版本迁移或多版本并存。
- 不做跨机器同步、云端账号体系或团队共享仓库。
- 不做可视化 Skill 编辑器，只支持文件系统中的 Markdown 和目录包。
- 不做 Skill 之间的依赖解析、依赖安装或依赖版本冲突处理。
- 不做长期后台任务系统；独立模式只覆盖一次性隔离对话执行。
- 不改变现有工具权限系统的用户确认语义，不让 Skill 白名单成为权限放行机制。
- 不改变 MCP 服务器配置格式或连接协议；Skill 只能引用当前系统可提供的工具或自身目录包声明的专属工具。
- 不把 commit、review、test 做成命令系统里的特殊硬编码逻辑，它们必须走普通 Skill 机制。

## 验收标准

- **AC1：单文件 Skill 可解析**  
  给定一个包含合法 frontmatter 和正文的 Markdown Skill，系统能读取唯一名字、一句话说明、工具白名单、执行模式、独立历史范围、可选模型和 SOP 正文；正文为空或必填字段缺失时，该 Skill 被跳过并记录原因。

- **AC2：目录型 Skill 可加载**  
  给定一个包含入口 Markdown、专属工具 schema 和实现脚本的目录型 Skill，系统能把它作为一个能力包发现；激活后完整 SOP 和专属工具可用于该 Skill；入口缺失或工具声明不完整时只跳过该 Skill。

- **AC3：三级覆盖正确**  
  当内置、用户、项目三个来源存在同名 Skill 时，最终可见的是项目目录版本；没有项目版本时使用用户版本；没有用户版本时使用内置版本。被覆盖版本不出现在帮助、补全、启动期 Skill 列表或加载结果中。

- **AC4：解析失败不阻断整体**  
  一个非法 Skill 文件存在时，其他合法 Skill 仍可被发现、展示、补全和加载；错误报告能指出非法 Skill 的来源和原因。

- **AC5：白名单缺失工具启动失败**  
  一个成功解析的 Skill 白名单引用不存在工具时，启动失败并指出 Skill 名称和缺失工具名；白名单合法时启动成功。Skill 加载工具即使不在白名单中，也仍然可被模型用于加载 Skill。

- **AC6：启动期只注入元数据**  
  启动后的系统上下文只包含有效 Skill 的名字和一句说明，不包含完整 SOP 正文、目录型 Skill 脚本内容或专属工具实现细节。

- **AC7：按需加载完整指令**  
  通过系统级 LoadSkill 工具激活某个 Skill 后，下一轮 Provider 请求的环境上下文包含该 Skill 的完整 SOP、参数替换后的内容和清晰标题；同一 Skill 重复激活会用最新有效加载结果替换旧快照，不会造成不可控重复注入。

- **AC8：多个 Skill 同时激活**  
  依次激活两个不同 Skill 后，后续 Provider 请求同时包含两个 Skill 的完整指令，顺序稳定，边界清楚；清空对话后两个完整指令都被移除。

- **AC9：共享模式写入主历史**  
  共享模式 Skill 被触发后，模型输出和工具结果按普通回合写入当前主会话历史；取消、异常或失败时不留下半提交消息。

- **AC10：独立模式摘要回流**  
  独立模式 Skill 被触发后，临时对话按配置带入指定历史范围运行；成功时主历史只收到摘要、关键结果和必要后续动作；失败时主历史只收到失败摘要和可诊断原因。

- **AC11：独立历史范围受控**  
  分别配置不带历史、最近部分历史、摘要历史和安全范围内全部历史时，独立对话实际收到的历史符合配置，并且不破坏工具调用与工具结果配对。

- **AC12：工具集合被白名单收窄**  
  Skill 执行期间，模型可见工具集合只包含白名单允许工具、该 Skill 专属工具和系统级 Skill 加载工具。尝试调用白名单外工具时，模型请求中本就不可见该工具；如果 Provider 仍返回未知工具调用，现有未知工具处理规则继续生效。

- **AC13：/skill 列表命令可用**  
  执行 `/skill` 时，系统列出当前可加载 Skill 的名称、来源优先级和一句话说明，并标识已激活 Skill；`/skill` 出现在 /help 和补全候选中。普通 Skill 不自动出现在斜杠命令候选中，也不能通过同名斜杠命令直接触发；同名 Skill 按三级来源覆盖后仍出现内部冲突时，启动失败并指出冲突来源。

- **AC14：热更新生效且保留激活快照**  
  运行中刷新 Skill 后，新增 Skill 出现在 `/skill` 输出中，修改后的说明用于后续展示，删除的 Skill 不再可被新加载，解析失败的 Skill 被移除并报告原因；已经激活的 Skill 继续使用激活时快照，直到 `/clear` 或显式重新加载同名 Skill 才切换版本。

- **AC15：/clear 清理激活状态**  
  执行清空对话后，当前会话边界和累计计数按现有规则重置，所有已激活 Skill 被清空；下一轮请求不再携带清空前激活的完整 SOP。

- **AC16：内置样板走统一机制**  
  commit、review、test 三个内置样板能在启动期以普通 Skill 形式展示，能通过同一 LoadSkill 工具触发，并接受同一套白名单校验、执行模式和参数替换规则；它们不会额外注册为特殊斜杠命令。

- **AC17：完整回归验证**  
  Skill 相关新增测试通过；现有命令系统、提示词管线、工具执行、权限确认、MCP、上下文压缩、会话恢复、记忆系统和终端渲染测试保持通过；静态检查保持通过。
