# 会话级权限授权修复 Spec

## 背景

当前权限确认在 `default` 模式下按调用目标进入确认。现有“本会话允许”会在内存中记录一条与当前完整命令或完整项目相对路径对应的精确 `allow` 规则，因此相同目标的重复调用可以复用，但连续执行不同命令时仍会再次确认。实测结果为：首次 `run_command(git status)` 选择会话允许后，第二次相同命令命中会话规则；随后 `run_command(git diff)` 又进入确认。

这使“本会话允许”无法满足用户减少同一会话内重复确认的预期，也容易让用户误以为选择没有生效。本次修复需要明确会话授权的覆盖范围，并保证它仍受危险命令黑名单、工作区沙箱和显式 `deny` 规则约束。

## 目标

- 在当前 OkCode 进程内，用户选择“本会话允许”后，后续属于同一授权范围的工具调用无需重复确认。
- 让授权范围可解释、可测试，避免把一次会话授权错误地升级为永久规则或无边界的全局放行。
- 保留权限系统的安全优先级：黑名单、路径沙箱和显式拒绝始终优先于会话授权。
- 会话授权仅保存在内存中；退出进程后失效，不写入任何 YAML 文件。

## 功能需求

- F1：会话授权范围
  - 对命令工具，会话授权默认覆盖同一命令工具的后续调用，不要求命令文本完全相同。
  - 对路径工具，会话授权默认覆盖同一路径类工具在当前工作区内的后续调用；路径仍必须经过现有工作区规范化和沙箱检查。
  - 对没有权限目标的工具，会话授权覆盖同一工具的后续调用。
  - 会话授权不得跨工具、跨工作区或跨 OkCode 进程复用。
- F2：安全优先级保持不变
  - 危险命令黑名单、工作区外路径或符号链接越界在任何会话授权下都拒绝。
  - 已命中的 `deny` 规则在任何会话授权下都拒绝。
  - 已命中的持久化 `allow` 规则和会话授权都不能改变上述终局拒绝。
- F3：确认结果与持久化边界
  - “仅本次允许”只放行当前调用，不创建会话授权。
  - “本会话允许”只更新当前权限管理器的内存状态，不写入项目或用户 YAML。
  - “永久允许”继续沿用现有项目本地 YAML 精确规则行为，不因本次会话范围调整而扩大持久化范围。
- F4：会话生命周期
  - 会话授权在同一 `PermissionManager` 服务的后续轮次和同一轮次的连续预检中可复用。
  - 创建新的权限管理器、恢复为新进程或 OkCode 进程退出后，会话授权消失。
  - `/clear` 是否清理会话授权不在本次修复中改变，继续遵循当前“进程级会话授权”契约。
- F5：可观察拒绝结果
  - 被黑名单、沙箱或显式 `deny` 拒绝的调用继续返回现有结构化权限失败结果，包含权限来源和 `executed=false`。
  - 允许路径不再触发确认时，工具执行结果和现有终端事件顺序保持不变。

## 非功能需求

- N1：兼容现有 `PermissionManager`、`ToolExecutor`、CLI 和终端确认接口，不改变 `strict`、`default`、`allow` 三档模式含义。
- N2：不引入新的磁盘格式、配置字段、跨进程同步或图形化权限管理界面。
- N3：会话授权匹配必须是确定性的，规则来源和拒绝来源可通过现有测试或结构化结果辨识。
- N4：修改保持 Windows 路径、大小写和现有工具权限目标语义兼容。

## 不做的事

- 不把会话授权实现为永久 `allow` 规则，也不修改 `.okcode/permissions.local.yaml` 的写入逻辑。
- 不放开危险命令黑名单、工作区边界、符号链接防护或显式 `deny`。
- 不把一次会话授权升级为所有工具、所有项目或所有 OkCode 进程共享的授权。
- 不新增用户级“默认允许”配置、不改变 `/permission` 命令和工具权限模式显示。
- 不重构 Provider、Agent Loop、MCP、Hook 或 Team 的无关逻辑。

## 验收标准

- AC1：在 `default` 模式下，首次 `run_command(git status)` 选择“本会话允许”后，后续 `run_command(git diff)` 等同一命令工具调用不再触发确认，并且工具正常执行。
- AC2：在 `default` 模式下，首次路径工具选择“本会话允许”后，后续同一工具的其他工作区内路径调用不再触发确认；工作区外路径仍被沙箱拒绝且工具执行次数为零。
- AC3：会话授权只在当前权限管理器内存中存在；重新构建权限管理器后，同一调用重新按默认模式进入确认；任何权限 YAML 均不新增会话授权记录。
- AC4：危险命令在已有会话授权、`allow` 模式或持久化 `allow` 规则下仍返回 `blacklist` 拒绝，子进程启动次数为零。
- AC5：显式 `deny` 规则在已有会话授权下仍返回原规则来源的拒绝，工具不执行。
- AC6： “仅本次允许”后，同一工具的下一次调用仍会再次确认；“永久允许”仍只对精确持久化规则生效。
- AC7：连续多个工具调用的 Agent Loop、确认输入异步等待、工具结果事件顺序及现有权限/终端测试保持通过。
- AC8：运行权限模块定向测试、相关集成测试、`uv run ruff check .` 和 `git diff --check` 均通过。

## 方案选择

1. **推荐：按工具权限范围记录会话授权**。会话规则不再绑定完整目标，只绑定工具及其权限目标类别；保留黑名单、沙箱、显式拒绝的前置检查。优点是直接解决连续不同命令的频繁确认，规则简单且容易解释；代价是用户在会话内首次授权某工具后，该工具后续目标会自动放行。
2. **保持精确目标规则，仅修复生命周期或匹配规范化**。安全范围最小，但无法解决用户描述的“每个不同命令都要点一次”，只适合问题实际来自管理器被重建或目标字符串不稳定的情况。
3. **会话内切换整体 `allow` 模式**。实现最简单，但会同时放开所有未命中规则的工具，授权范围过大，不推荐。
