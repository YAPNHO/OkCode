# OkCode 第十四阶段：Team Lead 长期团队协作 Spec

## 背景

OkCode 已经具备子 Agent 委派执行能力和子 Agent Worktree 隔离能力。第十二阶段解决了“主 Agent 可以启动独立子 Agent 执行任务”的问题，第十三阶段解决了“需要修改文件的子 Agent 可以在独立 Git worktree 中工作”的问题。

但现有能力仍然偏向一次性委派：主 Agent 把一个子任务交出去，等待后台结果回来；子 Agent 之间没有共享任务清单，也没有点对点通信；已经完成并停下的子 Agent 不能作为长期队员被恢复继续工作；主 Agent 仍然需要同时承担拆任务、派人、跟踪进度、审阅计划、处理消息和直接改代码的职责。

本阶段把主 Agent 升级为 Team Lead：它可以创建一个长期存在的小组，维护成员花名册、共享任务列表和成员邮箱，按任务依赖把工作派给多个成员并行推进。成员之间可以通过共享任务清单和点对点消息直接协作，Lead 只负责拆解、决策、审批、唤醒、终止和合并结果。对于需要更强隔离的成员，OkCode 可以在独立终端窗格中运行完整实例；对于轻量成员，也可以在同进程协程中运行。可用后端按环境优先级选择，不能在隔离能力不足时静默降级。

本阶段还增加 coordinator 模式：当配置能力开关和用户环境变量同时启用时，发起方进入协调者职责，只保留读类工具、必要 shell 能力和团队调度能力，不再直接使用普通文件写入工具完成代码修改。

## 目标

- 抽象一个长期存在的“小组”对象，持久化小组元数据、成员花名册、共享任务列表和成员邮箱。
- 支持 Team Lead 创建、恢复、查询、派生和唤醒团队成员，而不是每次都从零启动一次性子 Agent。
- 支持多种成员运行后端：独立终端窗格中的完整 OkCode 实例，以及同进程协程中的轻量成员实例。
- 按环境能力和显式请求选择成员后端；当要求的隔离等级不可用时，给出可诊断失败，而不是静默退回弱隔离。
- 给 Team Lead 和团队成员暴露团队专用协作工具，包括共享任务增删查改、任务依赖字段、点对点消息、广播消息和成员控制。
- 保证普通主入口、普通子 Agent 和非团队会话看不到团队协作工具。
- 支持需要审批的成员先提交计划，Lead 通过结构化批准或驳回消息控制其是否开始执行。
- 通过“名称注册表 + 邮箱文件”实现点对点消息；独立进程后端收到消息时还必须额外唤醒对应终端窗格。
- 支持成员自然停下后标记为空闲并通知 Lead；之后 Lead 再发消息时，OkCode 能从磁盘恢复该成员上下文继续指派。
- 支持 Team Lead 在全部任务完成后合并各成员工作目录的代码；可自动解决的冲突自动处理，无法处理时回滚并上报。
- 提供 coordinator 双锁模式：配置中启用能力，且用户通过环境变量主动启用后，发起方才被限制为协调者。

## 功能需求

- **F1：长期小组对象**
  OkCode 必须支持创建一个长期存在的小组。小组至少记录名称、负责人、成员花名册、持久化位置、创建时间、最后更新时间和当前状态。小组状态必须可以跨普通会话恢复。

- **F2：小组持久化位置**
  小组配置必须持久化到用户目录下按小组名隔离的文件夹。该文件夹中至少包含小组元数据、成员元数据、共享任务列表、名称注册表和各成员邮箱。OkCode 不得把团队运行状态混入项目源码目录，除非某个成员的工作目录本身是受管理 worktree。

- **F3：成员花名册**
  每个成员必须有稳定名称、角色说明、工作目录、运行后端、审批策略、当前状态、最近一次上下文引用和最后活跃时间。成员名称必须在小组内唯一，并经过安全校验，不能被用于路径遍历或覆盖其他成员状态。

- **F4：成员运行后端**
  OkCode 必须支持至少两类成员后端：独立终端窗格中的完整实例，以及同进程协程中的轻量实例。独立终端后端用于强隔离和长期可恢复工作；协程后端用于轻量并发。后端选择必须记录在成员元数据中，供后续恢复和诊断使用。

- **F5：后端选择与降级规则**
  当用户或 Lead 显式要求某种后端或隔离等级时，OkCode 必须严格满足该要求；当前环境不支持时必须失败并说明缺失能力。只有在请求声明“自动选择”时，OkCode 才能按环境优先级选择可用后端；选择结果必须可见，不能静默从强隔离降级到弱隔离。

- **F6：团队工具可见性**
  共享任务工具、点对点消息工具、广播工具、成员唤醒工具、成员终止工具和合并工具只能暴露给 Team Lead 和处于团队上下文中的成员。普通主入口、普通子 Agent、Hook 触发的一次性子 Agent、非团队会话均不得看到这些工具。

- **F7：共享任务列表**
  小组必须拥有共享任务列表。任务至少包含稳定标识、标题、正文、负责人、状态、依赖任务、阻塞原因、产出摘要、关联消息和更新时间。Team Lead 和成员必须能新增、查询、更新和关闭任务。任务依赖字段必须被持久化并能被查询，但本阶段只做基础可见性和人工调度，不实现复杂自动排程。

- **F8：任务状态一致性**
  对共享任务列表的并发写入必须保持文件一致性。OkCode 必须避免两个成员同时写入造成任务丢失、重复或 JSON/YAML 损坏。成员更新任务时必须保留其他成员已经写入的字段。

- **F9：名称注册表**
  点对点消息必须先通过小组名称注册表解析目标成员。注册表至少记录成员名称、邮箱路径、运行后端、当前状态、唤醒信息和最后活跃时间。发送方不得直接猜测目标邮箱路径；找不到目标时必须返回结构化失败。

- **F10：邮箱文件协议**
  每个成员必须有独立邮箱文件。一条消息至少包含发件人、收件人、正文、时间戳、是否已读、摘要、协议类型和可选关联任务。落盘时如果发起方未提供时间戳，OkCode 必须自动补当前时间；未显式指定已读状态时必须默认为未读。

- **F11：邮箱并发安全**
  邮箱写入必须通过锁文件或等价机制保证并发安全。拿不到锁时必须重试；锁超过过期阈值时可以视为陈旧锁并按规则接管。锁等待、接管和失败都必须可诊断。

- **F12：点对点消息与广播**
  Team Lead 和成员必须能向指定成员发送点对点消息，也能向小组广播消息。广播必须为每个目标成员产生可追踪消息结果；其中一个成员写入失败不得导致其他成员必然失败。

- **F13：结构化协议消息**
  消息协议必须支持普通文本消息、任务指派、任务状态更新、审批请求、审批结果、阻塞上报、完成通知、恢复指令和广播通知。协议消息必须能被人类阅读，也必须能被运行时解析。

- **F14：独立进程成员唤醒**
  当目标成员使用独立终端窗格后端时，消息写入邮箱后，OkCode 必须额外唤醒目标窗格，使其有机会读取邮箱并继续执行。唤醒失败时，消息不能丢失，发送结果必须明确说明“已落盘但未唤醒”。

- **F15：成员审批流程**
  对于标记为需要审批的成员，成员收到任务后必须先向 Lead 发送计划审批请求，不得直接修改文件或执行高风险操作。Lead 必须通过结构化审批结果批准或驳回。批准结果至少能表达批准、驳回、原因和附加约束；成员只能在收到批准后继续执行。

- **F16：Lead 任务发起流程**
  当用户目标需要团队执行时，Lead 必须把目标拆成带依赖关系的共享任务，写入小组任务列表，再按角色和工作目录派生成员。Lead 应持续根据任务完成状态、成员消息和依赖关系做决策，直到任务完成、失败或需要用户介入。

- **F17：成员生命周期**
  成员运行时可以处于待命、运行中、等待审批、阻塞、空闲、完成、失败、终止或不可恢复状态。成员自然停下后必须标记为空闲并通知 Lead；成员失败或被终止时必须保留最后上下文引用和可诊断原因。

- **F18：成员恢复**
  当 Lead 向已经空闲或停止的长期成员发送新消息时，OkCode 必须能够根据成员元数据和最近上下文引用恢复该成员，而不是重新创建一个无历史的新成员。恢复失败时必须说明缺失的上下文、后端或工作目录。

- **F19：工作目录与代码合并**
  对会修改代码的成员，OkCode 必须记录其工作目录和产出分支或等价变更来源。全部相关任务完成后，Lead 可以发起合并。合并必须先确认目标成员状态和变更来源，再把成员工作成果合并回发起方工作目录。

- **F20：合并冲突处理**
  OkCode 必须能区分自动可处理冲突和需要人工决策的冲突。能安全解决的冲突可以自动处理并记录依据；无法安全处理时必须回滚到合并前状态，保留成员产出引用，并向 Lead 或用户上报冲突文件、冲突类型和下一步建议。

- **F21：coordinator 能力开关**
  coordinator 模式必须受两把锁控制：项目或用户配置中先启用该能力，且用户通过环境变量主动启用。只有两者同时满足时，发起方才进入 coordinator 模式；任意一把锁关闭时，OkCode 必须保持普通模式。

- **F22：coordinator 工具约束**
  coordinator 模式启用后，发起方必须失去普通文件写入、补丁写入、删除、格式化等直接改代码工具，只保留读类工具、必要 shell 能力、团队派生、团队消息、成员终止和代码合并能力。保留 shell 是为了执行 Git 状态检查和合并流程，不应被当作绕过限制直接编辑业务代码的通道。

- **F23：coordinator 可见提示**
  coordinator 模式启用后，OkCode 必须在发起方可见上下文中明确说明当前是 coordinator，职责是拆解、派人、审批、跟踪、合并和汇报。模型工具列表也必须反映写文件能力已被剥夺。

- **F24：团队查询与诊断**
  OkCode 必须提供用户或 Lead 可见方式查询小组、成员、任务和消息状态。查询结果至少展示小组名称、负责人、成员状态、未读消息数量、进行中任务、阻塞任务、最近更新时间和可恢复性状态。

## 非功能需求

- **N1：兼容现有能力**
  未创建团队、未启用 coordinator、未使用团队工具时，普通对话、现有 Agent 工具、Hook 子 Agent、Worktree 隔离、命令系统、权限系统、上下文管理、Skill 和 MCP 行为必须保持不变。

- **N2：安全优先**
  团队成员不得绕过现有权限系统、工作区边界、工具安全等级、Hook 拦截和全局禁止规则。coordinator 模式不得成为通过 shell 随意改文件的后门。

- **N3：可恢复性**
  小组、成员、共享任务和邮箱必须落盘。进程退出或成员自然停止后，OkCode 应能恢复团队视图和成员上下文引用；无法恢复的部分必须明确显示原因。

- **N4：并发可靠性**
  多成员同时更新任务和邮箱时，不得损坏持久化文件。锁超时、陈旧锁接管、部分广播失败和唤醒失败必须被记录，并可被测试观察。

- **N5：可观测性**
  小组创建、成员注册、任务变更、消息发送、消息读取、审批请求、审批结果、成员唤醒、成员恢复、成员终止、合并开始、合并成功、冲突回滚和 coordinator 生效都必须有可测试或可日志化事件。

- **N6：测试友好**
  团队协作主流程必须能用临时目录、假终端后端、假协程后端、假邮箱和本地 Git 测试仓库确定性测试。测试不得依赖真实外网模型服务。

- **N7：Windows 友好**
  后端选择、路径持久化、锁文件、终端窗格唤醒和 Git 合并流程必须在 Windows 环境中可运行。路径处理必须使用绝对路径和安全规范化，不能依赖只在 Unix shell 下成立的行为。

- **N8：职责边界清晰**
  Team Lead 负责拆解、派人、审批、决策、汇总和合并；成员负责执行被分配的任务；共享任务列表负责记录工作状态；邮箱负责成员间通信。任何一个职责失败时，应能定位到对应层，而不是表现成普通模型失败。

- **N9：上下文可控**
  成员之间和成员到 Lead 的通知默认只注入摘要、任务标识和可追踪引用，不把完整会话历史直接塞回 Lead 上下文。需要恢复成员时才读取该成员的持久化上下文。

## 不做的事

本阶段明确不包含：

- 不实现跨机器、远程 Worker 或分布式团队调度。
- 不实现成员之间的实时流式通信；消息以邮箱落盘、读取和唤醒为边界。
- 不实现复杂自动任务依赖求解、优先级调度或关键路径优化；任务依赖只做记录、查询和 Lead 决策辅助。
- 不实现图形化团队看板或实时多窗格 UI。
- 不实现多人类用户协同编辑同一个团队。
- 不要求所有终端程序都支持窗格唤醒；不支持时必须诊断失败或选择用户允许的其他后端。
- 不让普通子 Agent 自动获得团队协作工具。
- 不改变现有 Agent 角色定义、Skill、Hook 条件语义和普通工具业务语义。

## 验收标准

- **AC1（覆盖 F1、F2、F3、N3）**：创建小组后，用户目录下出现按小组名隔离的持久化目录；其中包含小组元数据、成员元数据、共享任务列表、名称注册表和邮箱；重启会话后能查询到同一小组和成员花名册。

- **AC2（覆盖 F4、F5、N7）**：在支持终端窗格的环境中，请求强隔离成员会选择独立终端后端并记录后端信息；在不支持终端窗格且请求不允许降级时，启动失败并说明缺失能力；自动选择模式会展示实际选择的后端。

- **AC3（覆盖 F6、F22、F23、N1）**：普通会话和普通子 Agent 的工具列表中看不到团队协作工具；Team Lead 和团队成员能看到各自允许的团队工具；coordinator 生效时，发起方工具列表不再包含普通写文件工具，并显示 coordinator 状态。

- **AC4（覆盖 F7、F8、F16）**：Lead 能把用户目标拆成多条共享任务并写入依赖字段；多个成员并发更新不同任务后，任务列表仍保持完整、可解析，且不会丢失其他成员字段。

- **AC5（覆盖 F9、F10、F11、F12、F13）**：发送点对点消息时，运行时通过名称注册表找到目标邮箱，自动补时间戳和默认未读状态，并用锁文件完成写入；广播消息会分别产生每个目标成员的成功或失败结果；结构化协议消息能被写入并再次解析。

- **AC6（覆盖 F14）**：对独立终端后端成员发送消息后，消息先成功落盘，再触发窗格唤醒；当唤醒失败时，发送结果明确显示“已落盘但未唤醒”，目标邮箱中仍能看到未读消息。

- **AC7（覆盖 F15）**：需要审批的成员收到任务后先发送计划审批请求；未收到批准前不能执行写入或高风险操作；Lead 发送结构化批准后成员继续执行，发送驳回后成员停止并记录驳回原因。

- **AC8（覆盖 F17、F18、N9）**：成员自然完成后状态变为空闲并通知 Lead；Lead 后续向该成员发送新消息时，运行时从磁盘恢复最近上下文继续执行；恢复失败时返回缺失上下文、后端或工作目录的具体原因。

- **AC9（覆盖 F19、F20）**：多个成员完成代码修改任务后，Lead 能发起合并；无冲突时合并进入发起方工作目录并记录来源；可安全处理冲突时自动解决并记录依据；无法处理冲突时回滚到合并前状态，并报告冲突文件和成员产出引用。

- **AC10（覆盖 F21、F22）**：只打开配置能力开关或只设置环境变量时，coordinator 都不生效；两者都打开时才生效。coordinator 生效后，直接文件写入工具不可见，但读类工具、必要 shell、派人、终止、发消息和合并能力仍可用。

- **AC11（覆盖 F24、N5、N8）**：团队查询命令或等价入口能展示小组、成员、任务和消息状态，包括未读消息数量、阻塞任务、成员可恢复性和最近更新时间；关键团队事件能在测试或日志中观察到。

- **AC12（覆盖 N2、N4、N6）**：新增测试使用临时目录、假后端和本地 Git 仓库覆盖邮箱锁、陈旧锁接管、并发任务更新、审批流程、成员恢复、coordinator 工具过滤和合并回滚；全量现有测试保持通过。
